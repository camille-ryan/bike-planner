# V2 — Design notes

**Status:** open, in progress. Captures decisions and plans for the next batch of work.
**V1 line:** everything on `main` as of 2026-05-11 is **V1**. V2 changes may supplant V1 components (notably `cost.py` and the paired-SPT trunk DB) rather than building strictly on top.

V2 has two roughly independent threads:

1. **Cost function rewrite** — refine `cost.py` per design sessions; closes known V1 gaps and introduces a graded surface model.
2. **Amenity-aware day-stage routing layer** — precompute k-best paths between amenity-equipped towns within ~150 km of each other; foundation for daily-stage tour planning.

Related V1-era docs that V2 will partly subsume or supersede:
- `FUTURE_PROFILES.md` — proposed "separate cost from topology" refactor and tour-network two-tier idea. V2 picks up the cost-from-topology piece; the two-tier transit network is deferred to V3+.
- `feature_profiles_and_scenicness.md` (memory) — was the placeholder for this work.

## 1. Cost function rewrite

### 1.1 Decided changes

All four decisions reached in the 2026-05-11 design session. Targets: `pgrouting/cost.py`.

**Highway base table changes** (both `_HIGHWAY_COST_BIKE` and `_HIGHWAY_COST_NOBIKE`):

| Tag | V1 (bike / no-bike) | V2 (bike / no-bike) | Rationale |
|---|---|---|---|
| `cycleway` | 1.0 / 1.0 | **0.9 / 0.9** | Sub-1.0 floor; cycleway is *better than its length* — router will detour ≤11% to use one. |
| `track` | 1.1 / 5.0 | **1.1 / 1.1** | Drop bike-infra distinction. Only 3.4% of tracks carry explicit bike-infra tagging; the 5.0 NOBIKE value was an artifact of tagging diligence, not rideability. Let tracktype + surface multipliers differentiate. |
| `path` | 1.1 / 5.0 | **1.1 / 2.0** | Soften the no-bike-infra default. Failure mode on `path` is "annoying" (push the bike), not "illegal" (sidewalk). 2.0 lets the router use unsignalled forest paths when they save substantial distance. |
| `footway` | 1.1 / 5.0 | **1.1 / 5.0** | Unchanged. Footways without `bicycle=yes` are often legally pedestrian-only; the strong default is correct. |
| All others | unchanged | unchanged | |

**Surface filter — replace blacklist with graded multiplier:**

V1 hard-excluded `sand`, `mud`, `grass`, `earth`, `dirt`. V2 replaces this with a per-surface multiplicative factor. The walking-equivalent framing anchors the values (riding 10 m on sand ≈ riding 100 m on asphalt, including misery premium).

```
asphalt / paved / concrete / paving_stones / compacted   → 1.0
fine_gravel                                               → 1.1
gravel / pebblestone / sett                               → 1.3
cobblestone                                               → 1.7
dirt / earth / ground / unpaved                           → 1.5
grass / woodchips                                         → 3.0
sand / mud / ice / snow                                   → 10.0
(anything else / untagged)                                → 1.0
```

Multiplier stacks on top of highway base × tracktype. No surface is hard-excluded any more — hard excludes are purely access-driven (motorway, `bicycle=no|private|dismump`, `access=private` without explicit bike permission).

**New: `bicycle_road=yes` bonus.** Multiply final cost by **0.9** when `bicycle_road=yes`. Captures German Fahrradstraße / Austrian Fahrradstraße and similar legal designations — a regular road repurposed for bike priority. Stacks with the cycleway sub-1.0 (a cycleway tagged bicycle_road = 0.81; correct, stronger signal deserves stronger preference).

### 1.2 Known gaps (intentionally deferred)

These are *known* missing terms; V2 does not address them, but they should appear in the v2 `cost.py` docstring so future readers know they're open.

- **Spatial scenic signals** (landcover overhead/forest cover, water density, low-traffic neighborhoods). The "best touring segment" qualities (full tree cover, frequent water resupply, near-constant camping) on GAP+C&O are all *buffer-of-edge* signals, not edge tags. Out of scope for cost.py-as-edge-function. See §3 below.
- **Conditional access** (`access:conditional`, `seasonal=yes`). Mountain pass closures (e.g. Großglockner Nov–Apr) aren't expressed in `surface=snow`; they're in conditional access tags. Non-blocker for summer Graz→Cph tour. Defer until needed; fix at preprocess by evaluating conditional tags against tour date range.
- **Route relation membership** (`route=bicycle` with `network=icn|ncn|rcn|lcn`). Strongest single "this is a real touring route" signal. Per-edge tag enrichment needed at ingest. Defer to V3; covered conceptually in `FUTURE_PROFILES.md`.
- **Turn-aware routing** (fewer turns + dangerous turns). Requires per-`(prev_edge, this_edge)` costs — algorithm change to SPT preprocessing. Tracked as Phase B; see §1.4.

### 1.3 Phase A — elevation-based grade & curvy descent

The cost.py formulas are implemented; they activate when callers supply `grade_pct` and `sinuosity`. Defaults (0.0 / 1.0) are no-ops, so the existing per-tag ingest pipeline keeps working until Phase A.2 (DEM ingest + sinuosity computation) lands.

**Uphill** — pure quadratic on positive grade:

```
cost *= 1 + 0.028 × grade_pct²
```

Calibration (matches user cycling profile, `cost ∝ grade²` for any uphill):

| grade | factor |
|---|---|
| 1% | 1.028 |
| 3% | 1.252 |
| 5% | 1.700 |
| 6% | 2.008 ← "trouble to sustain" |
| 9% | 3.268 |
| 12% | 5.032 |

**Straight downhill** — peaked bonus, neutral by 10%, penalty above:

```
g = -grade_pct  # positive descent magnitude
cost *= 1 - 0.05·g + 0.005·g²
```

| grade | factor |
|---|---|
| -1% | 0.955 |
| -3% | 0.895 |
| -5% | 0.875 ← peak bonus (the "fun zone") |
| -8% | 0.920 |
| -10% | 1.000 ← bonus exhausted |
| -15% | 1.375 |

Peak bonus at g=5% matches both the user's stated "fun zone" and the terminal-velocity physics (~38 km/h on a loaded LHT, below the ~50 km/h threshold where brake management becomes the dominant concern).

**Curvy descent** — only on descents, multiplies into the straight-downhill factor:

```
if descending and curv > 0:
    cost *= 1 + 0.0005 × curv × g
```

`curv` is the total absolute bend angle (degrees) the rider will encounter looking *ahead* in their direction of travel, summed over a 300 m polyline window. Stored per edge as `curv_fwd` / `curv_rev` — forward and reverse directions carry different values so a steep descending edge captures the bend *ahead of it* even when the descent itself is on a straight stretch (e.g. straight downhill into a flat curve at the bottom). Without this, the curvy-descent penalty would only fire on the curve edge itself, where the grade is often near zero — exactly the wrong attribution.

Examples (final factor = straight-downhill × curvy multiplier):

| curv (degrees in 300 m window) | at -5% grade | at -10% grade |
|---|---|---|
| 0 (straight ahead) | 0.875 | 1.000 |
| 45° (gentle bend) | 0.973 | 1.225 |
| 90° (sharp turn ahead) | 1.072 ← bonus eaten | 1.450 |
| 180° (hairpin) | 1.269 | 1.900 |
| 540° (switchback group) | 2.056 ← Alpine territory | 3.700 |

The earlier sinuosity-ratio model (`actual_length / endpoint_distance`) was replaced because it (a) couldn't catch a single isolated curve at the end of a long straight descent — the ratio gets diluted by surrounding straight pavement no matter how wide the window — and (b) attributed all the danger to the curve segment itself rather than the upstream descent that creates the kinetic energy.

**Phase A.1 — formulas (done):** parameters added to `bike_edge_cost`; constants `_UPHILL_COEFF`, `_DOWNHILL_LINEAR`, `_DOWNHILL_QUADRATIC`, `_SINUOSITY_COEFF` at module scope.

**Phase A.2 — DEM ingest + sinuosity computation (next):**
- DEM source: **Copernicus EU-DEM v1.1**, 25 m EU-wide.
- Sample elevation at each vertex in `ways_vertices_pgr`. Persist as a new column on the vertex table.
- Per-edge `grade_pct = (elev_target - elev_source) / length_m × 100`. Stored on `ways` (asymmetric — `ways.reverse_cost` already accommodates).
- Per-way sinuosity computed at PBF ingest from node positions: `sum(haversine(n_i, n_{i+1})) / haversine(n_0, n_N)`. Persist on `ways`.
- Recompute step (per §2.1 refactor) calls `bike_edge_cost(..., grade_pct=..., sinuosity=...)` from the SQL/Python recompute job.

## 2. Profile separation refactor

V2 introduces three profiles: `direct`, `balanced` (= current `lht`), `scenic`. Per `FUTURE_PROFILES.md §1`, the cost-from-topology split should be done **once** to make subsequent profile work cheap.

### 2.1 Schema change (carried forward from FUTURE_PROFILES.md §1)

- `ways` keeps `gid, osm_way_id, source, target, length_m, is_oneway, is_ferry`, **plus raw OSM tags** needed for cost computation (`highway`, `surface`, `tracktype`, `oneway`, `bicycle`, `cycleway`, `bicycle_road`, `access`). ~2 GB extra at corridor scale; computed once at ingest.
- Costs move to `ways_cost_<profile> (gid, cost, reverse_cost)` — one table per profile.
- Per-profile recompute is a single SQL UPDATE over `ways`, tens of seconds.

### 2.2 Profile cost-function shapes

| Profile | Cycleway preference | Surface penalty | Grade penalty (V3) | Scenic signals (V3) |
|---|---|---|---|---|
| `direct` | Standard cycleway (1.0 base, no sub-1.0 bonus). Minimize distance + access. | Light (don't refuse rough surfaces). | Mild. | None. |
| `balanced` | V2 cost function as decided in §1.1. | Graded (V2). | Quadratic (V3). | Marked points only (V2-V3). |
| `scenic` | Strong cycleway bonus (e.g. 0.7). Penalize traffic-bearing roads more aggressively. | Same as balanced. | Stronger; prefer flat/rail-trail. | Heavy (V3). |

V2 ships `direct` and `balanced` only. `scenic` requires the spatial scenic signals (V3 work).

### 2.3 Supplants V1

- Single-profile `ways.cost` column → per-profile cost tables.
- V1 ingest re-runs PBF to change cost; V2 ingest re-runs SQL to change cost.

## 3. Amenity-aware day-stage routing layer

### 3.1 Motivation

Daily-stage tour planning is the next user-facing capability. The user's target is **100 km/day**, with partner-meets-daily-by-train constraint. The natural data structure is a graph of **amenity-equipped town pairs within ~150 km of each other**, with precomputed k-best paths. DP over this graph yields multi-day tours that satisfy daily distance + lodging + train-access constraints.

### 3.2 Endpoint eligibility

Inventory (AT + CZ + DE + DK from V1 ingest):

| Place type | Count |
|---|---|
| city + town anchors (total) | **3,212** |
| Lodging within 1 km of anchor | ~73% |
| Food within 1 km of anchor | ~98% |
| Both lodging + food within 1 km | **~73%** (~2,350) |
| Lodging within 2 km | ~82% |
| Both within 2 km | ~81% (~2,600) |

**Amenity filter (V2):**
- **Lodging within 1–2 km** (camp_site / wilderness_hut count for US tours; not for this Graz→Cph tour — user does not camp outside US).
- **Food within 1 km** (food coverage is essentially universal).
- `bike_service` is a **tour-level** constraint, not per-stop.

Tightening to "≥2 lodgings" or "lodging within 1 km strict" might be worth exploring — affects pair count meaningfully.

### 3.3 k-best paths per pair

k = 3, mapped onto the three profiles defined in §2.2 (`direct`, `balanced`, `scenic`). This subsumes "k-best" into the multi-profile design — the three diverse paths come *for free* from three profile builds, rather than from Yen's-style topological diversification on a single profile.

Pair scale, rough sizing:
- ~2,600 amenity-OK anchors.
- ~150 candidates within 150 km of each (depends on density; central Europe is dense).
- Ordered pairs: **~250–300k**.

### 3.4 Architecture decision (open)

**A. Substrate-based.** Extend the V1 paired-SPT trunk DB from the polyline corridor to the full anchor-pair neighborhood (~8× more pairs vs. V1 corridor). Store per amenity-pair just the **anchor sequence** (≪100 bytes/pair). Materialize polylines at query time by walking the 30 km trunk DB.

- Storage: ~80 GB per profile substrate × 3 profiles ≈ **~240 GB**. Pair index trivial.
- Build: ~57 h per profile (8× V1 corridor build). Total ~7 days for 3 profiles.
- **Iteration-friendly**: cost-function tweaks only require re-running the SQL cost recompute + paired-SPT build; pair index is just a graph search on city_graph.

**B. Canonical-polyline.** Bake one polyline per amenity-pair per profile (~5 GB total). No substrate dependency.

- Storage: **~5 GB total** across 3 profiles.
- Build: every profile tweak triggers a rebuild from the road graph. Slow iteration.
- Loses paired-SPT runtime flexibility (no offline reroute around closed edges).

**Leaning A** because the scenic cost function is still being designed and iteration speed matters. Revisit if 240 GB becomes operationally painful.

### 3.5 Supplants V1

- V1 trunk DB (`data/spt/lht/paired_trunks.db`) is scoped to a Graz→Cph polyline corridor with `--max-km` filter. V2 extends to full anchor-pair coverage (architecture A) or replaces with baked polylines (architecture B).
- Trunk DB schema may need to add `profile` column or split into `paired_trunks_<profile>.db`.

## 6. V1 → V2 migration

Practical order of operations:

1. **Cost.py rewrite** (§1) — small, self-contained change. Land first.
2. **Profile separation refactor** (§2.1) — modify `ingest_pbf.py` to persist raw tags; add `ways_cost_<profile>` tables; carve out a `compute_cost` step in `main.py`.
3. **Rebuild V1 corridor artifacts under the new cost** to validate the rewrite doesn't break end-to-end routing. Compare Graz→Wien output against V1 baseline.
4. **Build pair-DB substrate for `balanced`** (§3) — proves out architecture A or B.
5. **Build `direct` profile cost recompute + pair-DB.**
6. **`scenic` profile waits on V3.**

Each step independently shippable. V1 stays runnable on `main` until V2 reaches step 3.
